# engine-mesh-reuse

Unifies mesh generation so that a single `BRepMesh_IncrementalMesh` call produces triangulation shared by STL export, GLB export, and geometry inspection, rather than meshing the shape independently for each format.

## Requirements

### Single mesh per export

The CAD engine SHALL call `BRepMesh_IncrementalMesh` exactly once per export operation. The resulting vertex and face arrays SHALL be cached and reused for STL, GLB, and inspection consumers.

#### Scenario: One mesh call for STL + GLB

**Given** `generate_cad` is called with valid build123d code
**When** the shape is successfully generated by `gen_step()`
**Then** `BRepMesh_IncrementalMesh` SHALL be called once on the OCP shape
**And** the resulting triangulation SHALL be stored in a cache structure (vertex array, face array)
**And** both `_export_stl` and `_export_glb` SHALL read from the same cached triangulation

#### Scenario: Current dual-mesh behavior replaced

**Given** the current implementation calls `_extract_trimesh(shape)` for GLB (including its own `BRepMesh_IncrementalMesh` call)
**And** `_export_stl(shape)` makes a separate `BRepMesh_IncrementalMesh` call
**When** the unified mesh approach is active
**Then** the separate `BRepMesh_IncrementalMesh` calls in `_extract_trimesh` and `_export_stl` SHALL be replaced
**And** both functions SHALL receive a pre-computed cache of vertex/face/normal data

### Cached vertex and face arrays

The unified mesh SHALL produce cached arrays of vertices (as numpy float64), face indices (as numpy int32), and face normals (as numpy float64) that are consumable by both STL and GLB writers.

#### Scenario: Vertex array reused by STL

**Given** a cached mesh with vertices and face indices is available
**When** `_export_stl` writes the STL file
**Then** the writer SHALL use the cached vertex and face data
**And** the STL file SHALL be binary format (not ASCII)
**And** the STL SHALL be geometrically equivalent to what `StlAPI_Writer` would produce from the same mesh

#### Scenario: Vertex array reused by GLB

**Given** a cached mesh with vertices, face normals, and face indices is available
**When** `_export_glb` writes the GLB file
**Then** the writer SHALL use the cached vertex, normal, and face data
**And** the GLB SHALL be a valid glTF 2.0 binary file
**And** the mesh payload SHALL be populated from the pre-computed cache rather than iterating `TopExp_Explorer` over faces

#### Scenario: Cache populated from OCP triangulation

**Given** `BRepMesh_IncrementalMesh` has been performed on the shape
**When** the cache is populated
**Then** the system SHALL iterate `TopExp_Explorer` over faces once to collect all vertices, face indices, and normals
**And** the collected data SHALL be stored as contiguous numpy arrays
**And** face orientation (reversed/normal) SHALL be respected in face winding order

### Parallel STL + GLB export

STL and GLB exports SHALL run in parallel via `concurrent.futures.ThreadPoolExecutor` with a maximum of 2 workers.

#### Scenario: STL and GLB exported concurrently

**Given** the unified mesh cache has been populated
**When** `generate_cad` proceeds to export phase
**Then** STL and GLB exports SHALL be submitted to a `ThreadPoolExecutor(max_workers=2)`
**And** both futures SHALL be awaited before proceeding to inspection
**And** if one export fails, the other SHALL still be attempted

#### Scenario: STEP export precedes parallel phase

**Given** the export phase begins
**When** STEP is exported via XCAF
**Then** STEP export SHALL complete before the parallel STL+GLB phase begins
**And** STEP export SHALL use its own mesh (XCAF internal) and SHALL NOT consume the unified mesh cache

#### Scenario: Thread safety in OCP

**Given** the unified mesh cache is read-only after population
**When** STL and GLB writers read from the cache in parallel threads
**Then** no GIL contention SHALL occur on OCP calls because cache access is pure numpy/array operations
**And** the total STL+GLB phase time SHALL be ≤ max(STL_time, GLB_time) + small overhead

### Inspection reuses in-memory shape

The `inspect_geometry` tool SHALL operate on an in-memory `TopoDS_Shape` handle returned by `generate_cad` rather than re-reading the STEP file from disk via `STEPControl_Reader`.

#### Scenario: Inspection receives shape handle

**Given** `generate_cad` has produced a `TopoDS_Shape` from `gen_step()`
**When** `inspect_geometry` is called
**Then** the `inspect_step` function SHALL receive the in-memory shape handle
**And** the `STEPControl_Reader.ReadFile` round-trip SHALL be eliminated

#### Scenario: Inspection on retry uses handle

**Given** the agent is in a repair loop and has called `inspect_geometry` previously
**When** a retry of `run_cad_code` produces a new shape
**Then** the inspection SHALL use the new in-memory shape handle
**And** the STEP file SHALL still be written to disk for client download

#### Scenario: Fallback to disk read

**Given** `inspect_geometry` is called with a step_path that was not generated in the current session
**When** no in-memory shape handle is available
**Then** the system SHALL fall back to `STEPControl_Reader` from the STEP file on disk
**And** the behavior SHALL be equivalent to the current implementation

### Tier-driven mesh deflection

The `generate_cad` function SHALL receive a deflection parameter from the tier classification and SHALL pass it to the unified `BRepMesh_IncrementalMesh` call.

#### Scenario: Deflection passed from prompt to generator

**Given** the prompt assembly has classified the request tier
**When** `run_cad_code` is called
**Then** the tier SHALL be passed to `generate_cad` as a parameter
**And** the deflection values SHALL be selected based on tier:
- SIMPLE: linear=0.1, angular=0.8
- MODERATE: linear=0.05, angular=0.5
- COMPLEX: linear=0.02, angular=0.3

#### Scenario: Deflection affects mesh quality

**Given** a COMPLEX part with curved surfaces
**When** the fine deflection (0.02 mm) is used
**Then** the STL and GLB meshes SHALL have higher triangle count than default deflection
**And** the visual quality SHALL be appropriate for manufacturing review
