## Exploration: Face Picking in ManfacterCAD 3D Viewer

### Current State

The 3D viewer (`src/viewport/CadExplorer.tsx`) renders GLB meshes loaded via `useGLTF()` from Drei/Three.js. The model is displayed with OrbitControls for camera navigation, professional studio lighting, and auto-zoom centering. There is **zero interaction** with individual mesh surfaces — no raycasting, no hover/click detection, no face selection. The Canvas component from `@react-three/fiber` (v9) renders a `<primitive object={scene} />` with the loaded GLTF scene.

The GLB is generated by `backend/cad_engine/generator.py` via the Epic B path: `_mesh_once()` triangulates faces using `BRepMesh_IncrementalMesh` + `TopExp_Explorer(TopAbs_FACE)`, producing a `MeshCache` (vertices/faces/normals as flat numpy arrays). The mesh is then exported by `_export_glb_from_cache()` using `trimesh.Trimesh(...).export(file_type="glb")` — a **flat, un-attributed mesh** with no per-face color or ID information.

The in-memory OCP shape is stored in `_SHAPE_REGISTRY[model_id]` and accessible via `get_shape_handle()`. The `shape_glb_mesh_payload.py` module already has the concept of `face_runs_by_hash` mapping OCP face identity to triangle ranges — but this is only used in the text-to-cad selector pipeline, **not** in the viewer GLB export.

**Relevant versions:** Three.js 0.175, R3F v9, Drei v10, build123d (OpenCASCADE 7.8+), Python 3.11+.

### Approaches

#### 1. Position+Normal Face Matching (Recommended)

**Concept**: Raycast in Three.js → get world-space hit point + face normal → send to backend → backend iterates OCP faces via `TopExp_Explorer` → finds closest face by geometric proximity → returns face index/identity → LLM generates build123d modification code referencing that face.

**Frontend flow:**
1. Add `onPointerDown` handler to the Canvas or a transparent overlay mesh
2. Use `useThree()` to access `camera` and `raycaster`
3. On click: `raycaster.intersectObjects(scene.children, true)` to get hit info
4. Store `point` (world position), `face.normal` (world normal), `model_id`
5. Visual feedback: highlight the clicked face (change material emissive or add outline)
6. UI: show a floating action menu ("Make hole here", "Extrude this face", "Add fillet")
7. Send WebSocket message: `{ type: "face_pick", model_id, position: [x,y,z], normal: [nx,ny,nz], scale: 0.001 }`

**Backend flow:**
1. New function `find_ocp_face(shape, hit_pos_mm, hit_normal)` in `generator.py`
2. Iterate faces via `TopExp_Explorer(shape, TopAbs_FACE)`, for each face:
   - Get triangulation via `BRep_Tool.Triangulation_s(face, loc)`
   - For each triangle in the face, compute 3D distance from hit point to triangle
   - Check if projected point lies inside triangle (barycentric coords)
   - Compare triangle normal dot-product with hit normal (> 0.95 threshold)
   - Return best match (closest distance with normal match)
3. Return `{ face_index, face_type: "PLANAR"|"CYLINDRICAL"|..., face_area, face_center }`
4. LLM uses face index or geometric description to construct `part.faces()[index]` selector
5. LLM generates modification code referencing the selected face

**Pros:**
- Zero GLB format changes — works with existing viewer immediately
- No breaking changes to the CAD pipeline
- Deterministic: same geometry always maps to same face
- Face identity is stable within a session (same OCP shape reference)
- Reuses existing `TopExp_Explorer` face iteration pattern already in codebase
- Can handle any face type (planar, cylindrical, curved) correctly

**Cons:**
- Backend must recompute face matching on every pick (≈10-50ms for moderate models)
- Triangle-iteration per face is O(total_triangles) — acceptable under 50k triangles
- Position-only matching can be ambiguous on thin features or self-intersecting geometry
- Requires the shape handle to still be in memory (already managed by `_SHAPE_REGISTRY`)

**Effort:** Medium

---

#### 2. Embed Face IDs in GLB Mesh

**Concept**: Modify `_mesh_once()` to record which triangle range belongs to which face. During GLB export via trimesh, embed a `_FACE_ID` custom vertex attribute (one integer per vertex). In the viewer, read this attribute from the GLTF mesh geometry and use it on raycast hit.

**Implementation:**
- `_mesh_once()` already iterates face-by-face; add `face_tri_ranges: list[tuple[int, int, int]]` to return
- `_export_glb_from_cache()`: use trimesh with per-vertex face ID array, write as GLTF custom attribute (`_FACE_ID` with `SCALAR` type)
- Viewer: in `GlbModel`, read `geometry.attributes._FACE_ID` from each mesh
- On raycast hit: `faceIndex` → look up vertex indices → read `_FACE_ID` → done

**Pros:**
- Instant face identification in the viewer — no backend round-trip needed
- GPU-accelerated: raycasting is a single `intersectObjects` call
- Face ID travels with the GLB file (useful for offline inspection)

**Cons:**
- GLTF custom attributes require careful encoding (accessor type, componentType, bufferView)
- Trimesh's GLB export doesn't natively support custom per-vertex attributes — would need post-processing of the binary GLB or switching to a lower-level GLTF writer
- Must maintain face identity stability across re-meshing (if deflection changes, face triangulation changes)
- `hash(face)` in Python is not cross-process stable — need `TopoDS_Shape.HashCode()` from OCP
- Increases GLB file size by ~15-20% (one int32 per vertex)
- Requires changes to both backend GLB export and frontend loading

**Effort:** High

---

#### 3. GPU Picking via Encoded Render Target

**Concept**: Render a second pass where each face is colored with its encoded face ID. On click, read the pixel color from this offscreen render target and decode the face ID.

**Implementation:**
- Add a hidden `WebGLRenderTarget` to the R3F Canvas
- Use an `onAfterRender` callback or a second scene to render face-ID-colored meshes
- On click, `gl.readPixels(x, y, 1, 1)` to get the face ID color
- Decode RGBA → int32 face index

**Pros:**
- Pixel-perfect: handles overlapping geometry correctly
- No triangle-distance math needed
- Works for animated or dynamic geometry

**Cons:**
- Requires significant React Three Fiber plumbing (scene graph manipulation, render targets)
- Adds a full extra render pass per frame (or per click using `gl.readPixels` on cached target)
- Color encoding limited to ~16M IDs (RGBA8) — adequate for typical CAD parts (< 1000 faces)
- Complex to implement correctly with R3F's declarative model
- Still requires GLB modification to encode face IDs into vertex colors on backend

**Effort:** Very High

---

### Recommendation

**Approach 1 — Position+Normal Face Matching** — is the clear winner for the MVP:

1. **Lowest implementation risk**: No GLB format changes, no GLTF spec diving, no frontend Three.js custom attribute parsing
2. **Reuses proven patterns**: `TopExp_Explorer` face iteration and `BRep_Tool.Triangulation_s` are already production code in both `_mesh_once()` and `shape_glb_mesh_payload()`
3. **Immediate value**: Works with existing GLB files — no regeneration needed
4. **Graceful degradation**: Even if face matching is approximate, the LLM can interpret "pick the face near position X" and use geometric selectors like `faces().sort_by(Axis.Z)[0]`
5. **Backend computation is cheap**: For a typical CAD part with 50-200 faces and 10k-50k triangles, face matching via distance check takes < 20ms in Python/OCP

For a **production version**, we can later upgrade to Approach 2 (embed face IDs in GLB) once the workflow is validated and GLB format constraints are better understood.

### Data Flow for "Make a hole here"

```
1. User clicks face in viewer
2. Raycaster returns: { point: [12.3, 5.7, 0.0], normal: [0, 0, 1] }
3. Viewer highlights face, shows context menu
4. User selects "Make hole here" → chat: "Make a Ø10mm through hole here"
5. WebSocket message:
   {
     type: "face_pick",
     model_id: "a1b2c3d4e5f6",
     position: [12.3, 5.7, 0.0],
     normal: [0, 0, 1],
     scale: 0.001  // GLB→CAD mm conversion
   }
6. Backend converts position × 1000 → mm
7. find_ocp_face() matches face #3 (top face)
8. Returns: { face_index: 3, face_type: "PLANAR", center: [12.1, 5.8, 0.0], normal: [0, 0, 1] }
9. LLM prompt enriched with FaceInfo
10. LLM generates:
    top_face = part.faces().sort_by(Axis.Z)[-1]  # face with normal [0,0,1]
    hole = Cylinder(radius=5, height=20)
    hole_pos = (12.1, 5.8, -5)  # position from FaceInfo.center
    part -= Pos(*hole_pos) * hole
11. run_cad_code executes → new GLB → viewer updates
```

### Risks

1. **Face index instability across regenerations**: If the LLM uses `faces()[3]`, the index may refer to a different face after the part is modified (new faces added, topology changes). Mitigation: The LLM should prefer geometric selectors (`sort_by(Axis.Z)[-1]`) over raw indices. The `FaceInfo` should include enough geometric context (normal, center, bounding box) for the LLM to construct a robust selector.

2. **Normal matching ambiguity on curved surfaces**: A cylindrical face has varying normals. The raycast normal is the triangle normal, not the analytical surface normal. Mitigation: For curved faces, match primarily by position proximity, with normal used only as a tiebreaker. Use `BRepExtrema_DistShapeShape` for accurate distance computation.

3. **Model scale mismatch**: The GLB is scaled by `CAD_TO_GLB_SCALE = 0.001` (mm→m). The viewer is in meters, CAD is in mm. Mitigation: Always include the scale factor in the WebSocket message and convert consistently.

4. **Shape handle lifecycle**: The in-memory shape is released when the WebSocket session closes. If the user reloads the page, the handle is gone. Mitigation: Fall back to STEP file loading via `inspect_step()` — slower but functional.

5. **Three.js mesh structure**: The GLB scene may have nested groups, merged meshes, or multiple meshes. The raycaster must traverse all children. Mitigation: Use `raycaster.intersectObjects(scene, true)` with the recursive flag.

6. **Performance of face matching**: On large models (500+ faces, 100k+ triangles), iterating all triangles in Python could be slow (> 100ms). Mitigation: First filter faces by bounding box proximity using `Bnd_Box`, then triangulate-distance-check only candidates. For very complex models, precompute a kd-tree of face centers.
